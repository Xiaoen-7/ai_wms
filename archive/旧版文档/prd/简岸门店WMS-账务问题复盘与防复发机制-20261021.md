# 简岸门店WMS 库存账务问题：复盘与防复发机制

**成文日期**：2026-10-21
**适用对象**：本项目后续所有 PRD 撰写、评审、以及 AI 辅助产出流程
**一句话结论**：三类问题（账不守恒、入库无幂等、调拨差异不入库）全部通过了 v2.1 的既有评审——**不是某个环节"漏看"，而是现有评审结构里根本没有"账务闭合"这一项**。下文给出可直接落地的防复发机制。

---

## 一、这次发现了什么（速览）

| 编号 | 问题 | 级别 | 后果 |
|---|---|---|---|
| P0-1 | 调拨单有差异时**一件都不入库**，实到货品游离于所有账务科目之外 | P0 | 库房有货、账上没有；卖时扣无可扣、盘时变盘盈、再造一张差异单 |
| P0-2 | 库存账**无守恒恒等式、无校验机制**，且没有科目承载 P0-1 的差额 | P0 | 账错了无法自愈、无法提前发现 |
| P0-3 | 收货与调拨对**同一问题（实到≠单量）用了相反口径** | P0 | 系统内部自相矛盾，开发无法判断按哪个实现 |
| P1-1 | 四个入库按钮**无幂等键**，幂等只写在事件层 | P1 | 点两次按钮 = 入两次库；event_id 去重防不住（两次的 id 不同） |
| P1-2 | 离线暂存 7 天、恢复自动同步，**未定义去重与冲突规则** | P1 | 离线+在线双录 = 双倍入库 |
| P1-3 | 事件类型清单**两处定义不一致**（5.9.1 与 8.1） | P1 | 开发不知道该按哪份实现 |
| P2-1 | R3 规则"差异单未闭环"因 P0-1 永久误报 | P2 | 告警疲劳，真信号淹没 |

**最扎心的一条**：PRD 痛点 P4 原文写的是"收 8 件实到 7 件，差异挂账 2 个月成糊涂账"，G8 还设了"挂账清理 ≤7 天"的目标。**结果 v2.1 的设计把这个痛点原封不动搬进了系统**——只是把载体从 Excel 换成了数据库，而且更糟：Excel 里货还在、店长心里有数；系统里这 7 件是隐身的。

## 二、为什么没被发现（根因分析）

### 2.1 不是认知问题——有一个铁证

P0-3 那条**双标**是最硬的证据：

- `5.1.2 收货差异`：**"供应商确认前该批货按实点入库，差异部分挂账"** ← 写对了
- `5.4.3 调拨差异`：**"两端确认 → 闭环后调拨单置为已入库"** ← 写错了
- `5.1.1 收货`：**"实点与送货单不一致 → 拦截入库"** ← 和 5.1.2 自己打架

**同一个业务问题，团队写了三种口径，其中一种是对的。** 所以问题不在"不懂"，而在"没有把这几处放在一起看"。

### 2.2 评审做了什么、没做什么

从 v2.0 / v2.1 的版本记录可以完整还原既有评审维度：

| 评审检查项 | 做了吗 | 能发现本类问题吗 |
|---|---|---|
| 章节完整性（七段式 / 九章） | ✅ | ❌ |
| 目标可度量性（G1~G8 带度量方式与验收时点） | ✅ | ❌ |
| 功能边界数值（行数、件数、时限上限） | ✅ | ❌ |
| 测试用例条数（每功能 6~10 条） | ✅ | ❌ |
| 待确认项登记（27 项，含负责人与截止日） | ✅ | ❌（反而是掩盖源） |
| **跨功能库存账务闭合性** | **❌ 从未做** | ✅ **唯一能发现的** |

**前五项全过，正好绕开第六项。** 这不是偶然——这五项检查的都是"文档本身合不合格"，第六项检查的是"系统算不算得对"。二者是不同的评审类型。

### 2.3 三个具体的掩盖机制

**机制一：功能级验收的盲区**

每条 AC 单独看都成立：

- 5.1.1：`实点不一致 → 拦截入库并生成差异记录` ✔
- 5.4.2：`实到与单不一致时强制生成差异单才能继续` ✔
- 5.9.1：`同一事件重复上报不产生双倍扣减` ✔

三条都对，**但串起来跑一遍账就不平了**。没有任何一条 AC 是"全链路跑完后守恒恒等式成立"。测试用例数量（每功能 6~10 条，共 300+ 条）制造了"覆盖很充分"的错觉，实际测的全是功能内部行为。

**机制二：待确认项成了挡箭牌**

"在途货权归属"被登记为待确认项 4，标注"阻塞 B1、已逾期需催办"。这个标签让"调拨差异货不入账"看起来像是"等供应链拍板"的正常待决状态。

但这两件事必须分开：

| | 性质 | 能否待决 |
|---|---|---|
| 货权算调出店还是调入店 | 业务规则 | ✅ 可以，用配置化承接 |
| 实到的 7 件要不要入账 | 系统正确性 | ❌ **不可以** |

PRD 用前者的合法性，掩盖了后者。**这是整个事件里最值得记住的一课。**

**机制三：章节化写作让接缝处无人认领**

问题全部出在章节接缝处：

- 5.1.1 ↔ 5.1.2（收货内部矛盾）
- 5.1.2 ↔ 5.4.3（收货 vs 调拨双标）
- 5.4.3 ↔ 5.9.1（差异单 vs 库存事件）
- 3.6 状态机 ↔ 8.3 在途池（状态与记账脱节）

而 PRD 的组织方式是按功能分节，**接缝处没有归属章节**。第八章"账本与数据架构"本该承担这个职责，但它只写了"事件溯源 + 中央账权威"，没写"账务恒等式"——它管了架构，没管正确性。

### 2.4 关于 AI 辅助流程（skill / 环节）的判断

**结论：不是 skill 本身的问题，是流程编排缺了一个环节。**

具体拆解：

| 环节 | 现状 | 判断 |
|---|---|---|
| PRD 撰写 | 按章节逐节产出，每节质量合格 | ✅ 没问题，甚至偏细 |
| 自检/评审 | 检查章节完整性、目标可度量、边界数值、用例条数 | ✅ 执行到位，但**检查维度选错了** |
| 待确认项管理 | 27 项登记、负责人、截止日 | ✅ 规范，但**分类标准缺失**（没区分业务规则 vs 系统正确性） |
| **账务闭合推演** | **不存在** | ❌ **缺失的环节** |

所以准确说法是：**流程里没有任何一步要求"把库存变动按时间顺序推演一遍、检查每步 Σqty_delta 是否等于物理库存"。没有这个要求，就没有这个产出，也就没人能发现不守恒。** 这跟用什么工具写 PRD 无关——手工写、AI 写、团队写，只要流程里没有这一环，都会漏。

进一步说，AI 辅助反而放大了这个问题：AI 按章节逐节生成时，**每一节都会写得像模像样**（有边界、有异常、有 6~10 条测试用例），这会让"看起来很周全"的错觉更强。章节级质量高，不等于跨章节一致性成立。

## 三、防复发机制（可直接落地）

### 3.1 一级防线：PRD 模板级硬约束

**每个涉及库存变动的功能，验收标准中必须包含两类 AC，缺一不得通过评审：**

```
守恒 AC（必填）：
  本操作完成后，Σ库存账(可售+次品) + 在途池 + 待清理挂账量 + 寄存量
    = 期初 + Σqty_delta 成立

防重 AC（必填）：
  同一 client_txn_id 重复提交不产生二次库存变动
```

> 已写入 PRD v2.2 第 9.4 节"评审硬门槛"。

**为什么这条最有效**：它把"账务正确性"从一个抽象要求，变成了每个功能条目上必须有的一块内容。写不出这条 AC，说明这个功能对账务的影响没想清楚。

### 3.2 二级防线：全链路账务推演（评审必做项）

PRD 评审时做一次完整推演，**按时间顺序把货走一遍**：

```
收货 → 入库 → 调拨发货 → 调拨签收 →（差异）→ 盘点 → 销售 → 退货 → 次品
```

每一步记录一行：

| 步骤 | 调出店 | 在途池 | 调入店可售 | 挂账量 | 合计 | 守恒 |
|---|---|---|---|---|---|---|
| 发货 8 件 | −8 | +8 | 0 | 0 | 0 | ✅ |
| 签收 7 件 | −8 | 0 | +7 | +1 | 0 | ✅ |

**合计列必须恒为 0。** 出现任何非零，当场就是 P0。

本次修复就是靠这张表发现的：修复前同一张表的"签收"行合计是 −8，7 件凭空消失。

> 已写入 PRD v2.2 第 9.4 节。

### 3.3 三级防线：未决项必须分类

建立一条铁律：

| 类型 | 例子 | 能否阻塞开发 |
|---|---|---|
| **业务规则未决** | 货权归属、调拨权限、计提口径、坏账认定 | ✅ 可以，用"配置化 + 规则外置"承接 |
| **系统正确性** | 守恒、幂等、签收即入库、事件可追溯 | ❌ **不可以**，必须在 PRD 里定死 |

**禁止用"待确认项"标签包装系统正确性缺陷。**

自查问句：**"如果这个待确认项永远不拍板，系统会不会算错账？"** 会 → 它是系统正确性问题，不是业务待决项。

> 已写入 PRD v2.2 第 9.3 节。

### 3.4 四级防线：跨章节对照检查

对同一业务概念在多处出现的情况，评审时必须做横向对照表：

| 业务概念 | 出现的章节 | 口径是否一致 |
|---|---|---|
| 实到 ≠ 单量怎么处理 | 5.1.1 / 5.1.2 / 5.4.2 / 5.4.3 | ❌ 曾有三版 |
| 事件类型有哪些 | 5.9.1 / 8.1 | ❌ 曾是两版 |
| 调拨单状态有哪些 | 3.6 / 5.4.1 / 8.3 | ❌ 曾是三版 |

**凡是"清单在多处重复定义"的，一律收敛到单一事实来源。** v2.2 已把事件类型收敛到 8.1。

### 3.5 五级防线：文档组织方式调整

**在 PRD 中新增一个"不变量"章节**（v2.2 已建的 8.1.1 就是这个角色的雏形），专门承载跨功能的系统约束：

- 守恒恒等式
- 幂等键规范
- 各科目的定义与换算关系
- 禁止写入账外数量的规则

这个章节的定位是：**功能章节写"这个功能做什么"，不变量章节写"无论做什么，这些约束不能破"。** 有了它，接缝处就有了归属。

## 四、落地检查清单

下次写/评审 PRD 时，逐条打勾：

- [ ] 是否定义了库存的**全部科目**，且它们加总等于期初 + Σ事件？（不是只有"账面 = 期初 + Σ事件"）
- [ ] 是否存在**任何数量不在账上**的状态？（待核实、待确认、挂起、差异待处理……每一个都必须有科目）
- [ ] 每个写库存的按钮是否都有**业务幂等键**？（不是只有 event_id）
- [ ] 离线/断网场景的**同步去重规则**是否明确？幂等键在哪一刻生成？
- [ ] 同一业务问题在多个章节出现时，**口径是否一致**？
- [ ] 状态机里是否有**"因为业务未决所以货不入账"**的路径？（有就是 P0）
- [ ] 每个功能的 AC 里是否有**守恒 AC + 防重 AC**？
- [ ] 是否做了一次**全链路账务推演**，且合计列恒为 0？
- [ ] 27 个待确认项逐个过一遍：**哪些其实是系统正确性问题？**

---

## 五、一句话总结

> **v2.1 的问题不是"写错了"，是"没检查账"——评审检查的是文档合不合格，不是系统算不算得对。**
>
> 防复发的本质，是把"账务闭合"从一件**靠人想起来才做**的事，变成一条**不通过就不能上线的硬门槛**。
>
> 对 AI 辅助流程而言：不是换 skill，是在流程里加上"全链路推演"这一步，并且让 AI 在产出 PRD 时**自己先跑一遍这张表**——这比事后评审更省成本。
