# 简岸门店 WMS 埋点方案（总店运营视角）

> **依据**：[简岸门店WMS-PRD-20261019.md](prd/简岸门店WMS-PRD-20261019.md)（目标表 G1-G8 / 6.4 监控 / 7.3 变革管理）
> **视角**：总店运营——不关心技术日志，只关心两件事：**目标验收有没有达成**、**店员有没有真的在用**。
> **日期**：2026-10-20

---

## 一、最优先结论：账务事件即埋点，先复用后新增

PRD 采用 Event Sourcing（8.1 节）：所有库存变动本来就是不可变事件——

```text
事件 = { event_id, store_id, sku_id, qty_delta, 事件类型,
         关联单据号, 操作人, 时间戳, 来源系统 }
```

**这份 PRD 的独特优势：账务流水天然就是行为埋点。** 收货、盘点、调拨、退货每一步都产生事件，事件里有操作人、时间戳、单据号——运营要的"谁、什么时候、用了什么功能、干成了什么"全部在里面。

所以最优先的方案不是"加埋点"，而是：

1. **P0：把已有事件流直接接进运营看板**（零新增采集成本）
2. 只对"事件覆盖不到的行为"补埋点：页面停留、扫码中途放弃、降级发生、功能入口点击

### 表 1：目标验收埋点（P0，对齐 PRD 第二章 G1-G8）

| # | 指标 | 口径 | 数据来源 | 对应目标 | 上报时机 |

| 2 | 单次盘点时长 | 盘点单开始→提交耗时 | 盘点单事件对 | G2 | 盘点提交时 |

| 5 | 录错率（人工） | 差异单中"人工录错"归因笔数 | 差异单事件 | G6 | 月度 |
| 6 | 收货耗时 | 收货单扫码开始→确认入库耗时 | 收货单事件对 | G8 | 确认入库时 |

### 表 2：采纳行为埋点（P0，对齐 7.3 变革管理——最大风险）

> 「扫码枪 80% 吃灰」是这个项目最可能死掉的方式，所以"有没有在用"比"好不好用"更优先。

| # | 指标 | 口径 | 数据来源 | 用途 |
|---|------|------|----------|------|
| 1 | 扫码作业率 | 扫码完成的单据数 / 全部单据数（手动补录算未扫码） | 事件来源系统字段 | 每周看趋势，<80% 预警 |
| 2 | 功能渗透率 | 近 7 日用过核心功能的店员数 / 在岗店员数 | 事件操作人去重 | 门店健康分 |
| 3 | 扫码放弃率 | 进入扫码页后未确认就退出的次数 | **需新增埋点**（页面级） | 定位是"学不会"还是"不好用" |
| 4 | 回退 Excel 行为 | 系统可用期间手动改账 / Excel 导入次数 | 事件来源系统=手动 | 采纳倒退预警 |
| 5 | 降级发生次数 | 离线模式启用时长 + 次数 | **需新增埋点**（端上） | 区分"环境问题"与"不采纳" |

## 三、运营看板设计

**复用 PRD 5.20 总部数据自助查询 + 周一 08:00 周报邮件订阅**，新增一个「运营采纳周报」页签：

- **四卡总览**：扫码作业率 / 盘点差异率 / 归因覆盖率 / 降级次数
- **门店排行**：采纳健康分 = 扫码作业率 × 0.5 + 功能渗透率 × 0.3 + 差异率改善 × 0.2
- **预警名单**：连续 2 周健康分低于阈值的门店 → 自动生成驻店陪跑候选名单（直接对接 7.3 驻店陪跑资源）

**不建议做的**：UV/PV 大盘、页面热力图、漏斗细分——100 家店的 B 端工具，事件流已覆盖 80% 问题，先跑通 P0 再谈精细化。

## 五、隐私与边界

- 埋点数据用于**运营聚合**；店员个人操作明细用于考核时，规则须与 7.3 变革管理配套一致（考核什么就公开什么，避免"埋点变监控"引发抵触）
- 遵循 PRD 6.3：操作留痕 ≥3 年、字段级权限、总部不碰门店经营明细（埋点看板同理只做聚合）
